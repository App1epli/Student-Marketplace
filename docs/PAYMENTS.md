# Демо-оплата — часть проекта

Оплата интегрирована в действующий интерфейс маркетплейса и PostgreSQL. Она работает без регистрации: покупатель выбирает учебного студента на странице оформления. Реального платёжного провайдера, банковского перевода и списания денег нет.

## Что показать на защите

1. В каталоге нажать **Buy this item** у доступного товара.
2. На странице **Checkout** выбрать **Demo buyer**. Продавец не появляется в списке покупателей своего товара.
3. Выбрать **Demo card**, оставить результат **Approved**, нажать **Simulate payment**.
4. Показать демо-чек: сумма, товар, покупатель, продавец, способ оплаты, статус и уникальный reference. Чек можно распечатать.
5. Открыть **Purchase history**: заказ и его статус сохранены в PostgreSQL; товар отмечен проданным.
6. Для другого товара выбрать **Declined**: появится сообщение об отказе, заказ не создаётся, товар остаётся доступным. Поменять результат на **Approved** и повторить.
7. Показать **Bank transfer** — успешный перевод симулируется внутри приложения, банковские реквизиты не нужны.
8. Показать **Cash at pickup**: заказ создаётся со статусом **Pending**, а не оплачено.
9. Нажать **Cancel checkout** до подтверждения: покупка не создаётся.

**Что реализовано:** интерфейс оплаты, связь с бэкендом и базой, серверная проверка суммы/покупателя/наличия товара, статусы, чек, отказ, повторная попытка и защита от дублирования заказа.

**Что симулируется:** ответ платёжного сервиса. `Approved` / `Declined` — учебные сценарии, не ответ банка. Успешная онлайн-оплата помечается **Demo paid**. Полей для настоящего номера карты или CVV нет.

## Файлы

- `frontend/templates/checkout.html` — форма и итог заказа.
- `frontend/templates/receipt.html` — демо-чек и печать.
- `frontend/static/checkout.js` — переключение способов, подсказок, блокировка повторного нажатия.
- `frontend/static/styles.css` — оформление и адаптивная версия.
- `backend/payments.py` — проверка покупки, симуляция результата, защита от повторной отправки.
- `backend/app.py` — GET/POST `/checkout/<product_id>` и GET `/payments/<reference>`.
- `backend/migrations/001_demo_payments.sql` — поля оплаты в существующей таблице покупок.
- `tests/test_app.py` — интеграционные проверки с PostgreSQL.

## Данные и миграция

`purchases.payment_status` содержит `Demo paid`, `Pending` либо `Not recorded` для старых записей. `payment_reference` — уникальный UUID, который используется для чека и повторной отправки одной формы. Старые покупки сохраняются, их статус не меняется на «оплачено» задним числом.

Перед публикацией новой версии один раз выполнить из корня:

```powershell
python -m backend.app --migrate-db
```

Команда читает `DATABASE_URL_UNPOOLED` или `DATABASE_URL` из окружения / корневого `.env`, обновляет схему без загрузки демотоваров. Версии миграций фиксируются в `schema_migrations`; повторный запуск безопасен. В новой пустой базе `--init-db` также применяет миграции.

Платёжных ключей или новых переменных Vercel не требуется. После миграции достаточно Commit / Push и успешного нового деплоя.

## Подключение логина другим участником

В `backend/payments.py` есть функция `demo_buyer_id(form)`. Сейчас она читает выбранный учебный аккаунт. После реализации логина нужно получать student_id из проверенной серверной сессии, убрать выбор покупателя из формы и использовать ту же проверенную личность в старом маршруте `/purchase`. Дополнительно ограничить просмотр `/payments/<reference>` и `/sales` владельцем покупки / продавцом и добавить CSRF-защиту форм с сессионной авторизацией.

Это точка для дальнейшей интеграции, а не готовая авторизация: сейчас интерфейс явно обозначен как учебный, а история покупок общая.

## Проверки

```powershell
python -m unittest discover -s tests -v
```

Для полной проверки задайте `TEST_DATABASE_URL` отдельной PostgreSQL-базой. Тесты создают временную схему и затем удаляют её. Не задавайте URL рабочей базы ради тестирования. Проверяются также конкурентные запросы, повторное использование reference и подмена цены в форме.
